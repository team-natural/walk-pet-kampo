# 00_INTAKE.md — 案件ヒアリング正本

## このセクションの目的

本ファイルは、顧客ヒアリング・既存資料・コンサル所感を「生の事実 + 引用 + 仮置きラベル」で集約する **案件入力の正本** です。BIZ-01 以降の仕様書を AI または人間が初稿生成する際の唯一の入力源として参照します。

## 0. 編集ルール

- **書く人**: コンサルタント（または PdM）
- **読む対象**: 後続仕様書を起こす AI、案件参加者
- **AI の編集権限**: 読み取り専用。AI が再構成・要約する場合は別ファイルへ
- **更新の流れ**: 顧客から新事実が出たら、まず本ファイルへ追記。仕様書の修正はその後
- **既存記述は消さない**: 古い前提も取り消し線で残し、いつ何が変わったかを §11 変更履歴で追える形にする
- **発言の引用**: `> 「...」（発言者, 日付）` 形式
- **仮置き表記**: コンサルの推測・補完は末尾に `[Assumed: 根拠 / 確認先]` を付ける
- **開示区分**: front-matter `disclosure: internal-only` を原則とする。顧客開示する場合は別ファイル（`00_INTAKE_customer.md` 等）を作成して共有する

> 本プロジェクトは 00_README §0-1 が定義する「パターン A」の範囲を超えるマーケットプレイス事業だが、技術基盤は本リポジトリ（`site-template` 由来の Astro + Cloudflare 構成）を継続する（GOV-01 D-006）。以下は別リポジトリで記録されていた本ヒアリング内容を、本リポジトリの技術方針に合わせて移行したもの。

## 4. 顧客発言の生記録

トピック別にサブセクションを追加し、引用形式で残す。本案件は口頭ヒアリングではなく提示された仕様書ドラフトが情報源のため、引用は当該ドラフトの原文から抜粋する。

### 4-1. サービスコンセプト

> 「保護犬と触れ合いたい一般利用者と、保護犬を管理する保護団体をつなぐ、お散歩体験の予約・マッチングサービスを提供する。」（仕様書ドラフト §1, 2026-08-16）

→ コンサル所感: 一般的な「コンテンツ主体サイト + 軽量 CMS」テンプレとは異なり、**二者間マーケットプレイス**（参加者 ⇄ 保護団体）+ **運営による審査・仲介** という構造。Organization（保護団体）は課金される側ではなく、参加費の一部を**受け取る側**である点が本テンプレ標準（マルチテナント SaaS 想定外 — 00_README §2-2）と大きく異なる。GOV-01 D-006 の通り、本プロジェクトはこの差分を承知のうえで本テンプレート基盤を拡張して実装する。

### 4-2. ターゲットユーザー

> 「利用者は、自分の地域で活動する保護団体やお散歩募集を探し、参加費を支払って保護犬とのお散歩体験に参加する。」（仕様書ドラフト §1, 2026-08-16）

→ コンサル所感: エリア起点の検索（現在地からの距離、都道府県・市区町村）が主要な発見導線。位置情報（ジオコーディング）が技術要件に加わる（DEV-01 §2、GOV-01 D-009）。

### 4-3. 差別化ポイント・目的

> 「参加費の一部を保護団体へ還元することで、利用者が保護犬と触れ合いながら、保護活動を支援できる仕組みとする。」（仕様書ドラフト §1, 2026-08-16）

→ コンサル所感: 差別化はマネタイズ構造そのもの（1 回 500 円、団体還元 400 円 / システム利用料 100 円）。決済 → 団体への月次振込という資金フローの正確な実装が事業の根幹（DEV-01 §2、GOV-01 D-008 の Stripe Connect 採用）。

### 4-4. 技術方針

> （本仕様書は）「技術スタック：本仕様書の対象外」（仕様書ドラフト冒頭メタ情報, 2026-08-16）

→ コンサル所感: 技術選定は本リポジトリ（`site-template` 由来：Astro SSR + Svelte + Cloudflare Workers/D1/R2/KV）に一本化する（GOV-01 D-003）。参考サイト（うんぽぽさんぽ、Next.js 製と推測 `[Assumed: URL の実装から / 確認先: 未検証]`）の技術は踏襲しない。技術選定の唯一の正本は DEV-01。

### 4-5. ビジネスモデル

> 「初期の基本料金は以下とする。参加者1名・1回：500円。内訳：保護団体への還元対象額：400円、システム利用料：100円。」（仕様書ドラフト §12-1, 2026-08-16）
> 「会計・法務上の整理が完了するまでは、仕様上「寄付金」ではなく「団体還元対象額」として管理する。」（仕様書ドラフト §12-1, 2026-08-16）

→ コンサル所感: **サブスクリプションではなく都度課金（トランザクション課金）**。BIZ-03 は本テンプレート標準の「プラン別月額」構造ではなく、単価 + 内訳 + 従量（予約件数）モデルで再構成する。

### 4-6. ロール設計

> 「一般閲覧者」「お散歩参加者」「保護団体ユーザー」「運営管理者」の 4 区分（仕様書ドラフト §4, 2026-08-16）

→ コンサル所感: 本テンプレート標準の「admin/editor の少数ロール」構造とは対応が異なる。

- 「一般閲覧者」はアカウント種別ではなく、ログインしていない匿名訪問者を指す。`apps/public` の公開ページは認証なしで閲覧できるため、AdminUser / OrganizationMember / Walker のいずれにも対応するアカウント実体は存在しない
- Platform ロール: 原文にロール区分の明示は無いが、当初は業界一般的な構成を踏襲して `super_admin`（運営者）+ CS 対応ロール `support` の 2 ロール構成を仮置きした（旧設計 — GOV-01 D-004）。その後、実際の運営体制が Tech Lead / PdM 等の兼務前提の少人数チームであり、書き込み不可の read-only な専任サポート担当を分けて運用する実態がないという事業側の確定方針を受け、追加ロールを持たない単一ロール `admin`（運営者）に統合した（GOV-01 D-011（D-004 を置換））。`apps/admin` の AdminUser として実装する（GOV-01 D-007）
- Organization（保護団体）ロール: 原文は「保護団体ユーザー」を単一区分としてのみ言及するが、サイトマップに所属メンバー管理画面が存在することから団体内に権限差（管理者 / スタッフ）があると判断し `org_admin` / `org_staff` の 2 ロールとして設計する（構造の正本は PRD-01 §1-2）`[Assumed: サイトマップの記述から補完 / 確認先: 事業責任者]`。`apps/public` の OrganizationMember として実装する（GOV-01 D-007）。この 2 ロール構成は GOV-01 D-011 でも変更していない
- 「お散歩参加者」は Organization に所属しないプラットフォーム直属の利用者として設計する。`apps/public` の Member（Walker）として実装する

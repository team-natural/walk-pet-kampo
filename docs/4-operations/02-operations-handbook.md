# 02-operations-handbook.md — 運用ハンドブック

## このセクションの目的

リリース後の日常運用に **最低限必要な実作業** を 1 冊に統合する：サポート窓口（§1）、インシデント初動（§2）、リリース・ロールバック実作業（§3）、バックアップ・データ保持（§4）。**本サービスはお散歩参加者（Walker）が保護犬と身体的接触を伴う「お散歩」を行うマーケットプレイスであり（`Decided` — GOV-01 D-006）、システム障害だけでなく咬傷・逃走等の動物・人的安全事故の初動（§2）が通常の SaaS より重要度が高い**。技術面（デプロイ基盤・ロールバック・Cron Triggers 等）は Cloudflare Workers 前提の実作業手順を正本とし、本書では技術選定そのもの（プロダクト名の妥当性）は扱わない — 選定理由は DEV-01 §1・§2 を参照。ロールバックの判断基準は DEV-08 §5、SLA 数値は OPS-01 §3 が正本であり、本書は実作業手順のみを持つ。

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 下書き + Tech Lead / サポート担当 確定）
- 人間確認必須: 実際に守れる受付時間、体制人数で回るエスカレーション、動物・人的安全事故対応フローの実行可能性、ロールバック手順の実行可能性

---

## 0. 対応時間の原則（全章共通）

- 障害対応・サポート対応は **業務時間内（平日 9:00〜18:00）のベストエフォート** とする。
- 時間外・休日は自動アラート（監視・エラー通知）の記録のみを行い、**対応は翌営業日** とする。24/7 の人的オンコールは置かない。
- 重大な動物・人的安全事故（咬傷・逃走等）については、団体スタッフが警察・獣医療機関等への一次対応を自ら行うことを前提とし、運営（Platform）への正式な報告は翌営業日でも受け付ける旨を保護団体向けガイドに明記する（`[Assumed]` — GOV-02 TBD-21）。一次対応そのものを遅らせる意図ではなく、運営への報告のタイミングに §0 の原則を適用するものである。
- 体制は **Tech Lead / PdM / サポート担当** の少数ロール（兼務前提）で構成する。

## 2. インシデント初動

### 2-1. 重大度定義と解決目安

システム障害と、保護犬・参加者の安全に関わる事故報告（PRD-03 FG-12）の両方を対象とする単一の重大度体系を用いる。`incidents.severity`（DEV-07 §5-15）はこの定義値をそのまま格納する。

| Severity | 定義 | 例 | 解決目安 |
| --- | --- | --- | --- |
| **P0（Critical）** | サービス全体停止、個人情報漏洩、決済の二重課金、重大な咬傷・逃走等の動物安全事故 | アプリ全停止、犬の逃走で行方不明 | **当日中（安全事故は団体の一次対応後、速やかに運営へ報告）** |
| **P1（High）** | 主要機能の停止、決済・Stripe Connect 送金不可、通院を要する怪我等の事故 | 予約・決済フロー全停止、参加者が咬傷で通院 | **1 営業日以内** |
| **P2（Medium）** | 一部機能の停止、軽微な事故・トラブル | 特定団体の `walk_slots` が表示不可、軽微な物損 | **3 営業日以内** |
| **P3（Low）** | UI 不具合、軽微な性能劣化、苦情レベルのトラブル | 一部画面の表示崩れ、マナーに関する苦情 | **次回リリース / 通常対応** |

> 上記は運用目安であり、正式な SLA ではない（SLA は OPS-01 §3）。時間外に検知したものは §0 の原則により翌営業日起算とする。

### 2-2. 障害・事故に含めないもの

| 除外区分 | 対応方針 |
| --- | --- |
| 顧客起因の誤操作・誤設定 | 操作ガイドを案内、必要に応じデータ修正を支援 |
| 契約範囲外の要望（保護犬の飼育相談等） | OPS-01 §2 の契約範囲を説明し、要望として記録 |
| 外部サービス起因のみの問題（Stripe / Stripe Connect・Google Maps Geocoding・Cloudflare 基盤障害等） | 外部ステータスページを案内し復旧待ち（ベストエフォート） |
| 団体・参加者間の個人的な感情的対立で安全上のリスクがないもの | 当事者間での解決を案内（OPS-01 §6） |

### 2-3. 初動フロー

```
1) 検知（監視アラート / ユーザー通報 / 団体スタッフからの事故報告）
2) Tech Lead が重大度判定（P0〜P3）・対応チャネルで状況共有開始
3) P0/P1（システム障害）: 復旧最優先で原因究明・暫定対応（ロールバック判断は DEV-08 §5、実作業は §3-3）
   P0/P1（動物・人的安全事故）: 団体側の一次対応（通院・警察・保健所連絡等）を尊重しつつ、
     運営は事実確認・記録・関係者への連絡調整に専念する。`incidents` レコードの起票が
     `reported`（P0/P1 の場合は運営へ即時通知が飛ぶ — DEV-09 §2-10-3）の時点でこのフローの
     起点となる
   P2: 担当者アサインの上、通常対応
   P3: Issue 化して次回リリースに組み込み、または通常サポート対応
4) 復旧確認 → 顧客通知（システム障害時は §2-4）
5) P0/P1 は簡易ふりかえりを GOV-01 に記録（原因・影響・再発防止策）。安全事故は `incidents` レコード
   （DEV-07 §5-15、DEV-09 §2-10）の `prevention_measures` に再発防止策を、`resolved_at` に解決日時を
   必ず記録した上で `closed` へ遷移させる（PRD-03 F-12-03）
```

### 2-4. 顧客通知基準（システム障害時）

| Severity | 通知タイミング | チャネル | 対象 |
| --- | --- | --- | --- |
| P0 | 重大度判定後、速やかに（30 分以内目安） | アプリ内バナー + メール | 全ユーザー |
| P1 | 判定後 1 時間以内目安 | アプリ内バナー + 影響ユーザーへメール | 影響ユーザー |
| P2 | 復旧見込み判明時 | アプリ内バナー | 影響ユーザー |
| P3 | 通知不要（次回リリースノートに記載） | — | — |

動物・人的安全事故の場合、対外的な通知（プレスリリース等）の要否は PdM・事業責任者が個別判断する（定型フローに含めない）。

### 2-5. 個人情報インシデント

内部報告・行政報告・本人通知の期限とフローは **DEV-02 §12 を正本** とする。検知した時点で他の作業に優先して同フローを開始する。

### 2-6. 管理画面からの締め出し（Cloudflare Access）

`apps/admin` は Cloudflare Access の背後にある（GOV-01 D-031、DEV-02 §1-1）。**ポリシーの誤設定・ID プロバイダの障害は、運営者全員が管理画面に入れない状態を作る**。決済の返金や事故対応が必要な時間帯に起きると、障害対応そのものが止まる。

| 項目 | 内容 |
| --- | --- |
| 予防 | **ブレークグラス用の第 2 ポリシーを常設する**（主 IdP とは別の IdP、またはサービストークン）。主ポリシーの変更時に同時に壊れない独立した経路にすること |
| 切り分け | 管理画面が 403 を返す場合、Access のログイン画面が出るか（= Access 到達前）／ログイン後に 403 か（= アプリ側の `ctx.access` fail-closed）で原因が分かれる。後者は Access アプリケーションが Worker から外れている |
| 復旧 | Zero Trust ダッシュボードでポリシーを修正する。**アプリ側のコードを変更して Access を迂回させない** — 一時回避のつもりの変更が恒久化する |
| 担当 | Access アプリケーションとポリシーの管理者は Tech Lead。ポリシー変更は本番デプロイと同じ扱いで記録する |

Access が不通でも、Cron Triggers による月次 Payout 集計（§4-3）と Stripe Webhook（`apps/public`）は影響を受けない。止まるのは人間の操作経路だけである。

## 3. リリース・ロールバック実作業

デプロイ基盤・環境構成・CI/CD・デプロイゲートは DEV-08 §1〜§6 を参照。デプロイは **main / dev への push 起点で Cloudflare Workers Builds が自動実行** するため、本章は人間が行う確認作業とロールバック実作業のみを定義する。

### 3-1. 通常リリース手順

```
1) リリース対象 PR を集約し、CI（`pnpm check` = フォーマット / Lint / 型チェック、全テスト。Turborepo で
   apps/public・apps/admin それぞれに対して実行される）全 Pass を確認
2) リリースノート（GitHub Release Draft）を作成
3) main へ PR 経由でマージ → Cloudflare Workers Builds が `wrangler deploy` を実行（無停止。
   apps/admin 側は D1 マイグレーション適用が deploy に前置される — DEV-08 §3-2）
4) ヘルスチェック（全エンドポイントの定義は DEV-08 §9）
   curl https://{APP_URL}/api/v1/health
   curl https://{APP_URL}/api/v1/health/db
   curl https://{APP_URL}/api/v1/health/kv
   curl https://{ADMIN_URL}/api/v1/health/batch   # Cron Triggers（月次 Payout 集計・データ保管期限削除）の直近成功時刻
5) スモークテスト（§3-2）
6) デプロイ直後はエラー率・メトリクスを Cloudflare ダッシュボード（Workers Logs / Analytics）
   または `wrangler tail` のライブログで監視
   （ロールバック発動条件は DEV-08 §5 — 本書では再掲しない）
7) 異常なし → リリース完了報告 + GitHub Release を Publish
```

マイグレーションを含むリリースは、事前に staging で dry-run し、無停止可能なこと・前方互換であること（DEV-08 §4、D1 マイグレーションは forward-only）を確認してからマージする。**決済・還元関連テーブル（`payments` / `payouts`）の変更は、金額計算・Stripe Connect 送金額に影響しないことを重点確認する**（DEV-08 §5・§6-2、GOV-01 D-008）。Payout の集計ロジック（月次 Cron Triggers、DEV-09 §2-9）に関わる変更は、staging で少なくとも 1 サイクル分の集計結果を実データ相当で突合してからマージする。

### 3-2. リリース後スモークテスト

```
[ ] トップページ正常表示（エラー・レイアウト崩れなし）
[ ] ログイン / ログアウト動作（Walker・保護団体スタッフ・運営の 3 系統アカウント）
[ ] お散歩募集検索 → 予約 → 決済（Stripe テストカード、staging）の一連の動作
[ ] 保護団体登録申請フォームの送信・通知確認
[ ] お問い合わせフォーム送信・通知確認
[ ] HTTPS 有効確認（証明書エラーなし）
```

### 3-3. ロールバック実作業

判断基準は **DEV-08 §5 が正本**。該当したら以下を実行する（迷ったらロールバックを優先）。

```
1) コードのロールバック：
   Cloudflare ダッシュボード（Workers > Deployments）または
   `wrangler deployments list` で前デプロイメントを確認し、`wrangler rollback` で戻す
2) マイグレーションを伴う場合：
   - 前方互換マイグレーション → D1 はそのまま（コードのみ戻す）
   - 破壊的マイグレーション → 戻すのではなく、新規マイグレーションで修正
3) データ修正が必要な場合（特に payments / payouts の金額誤り）：
   - メンテナンスモード相当の仕組みは KV フラグ + 各アプリの `src/middleware.ts` での判定で実現する
   - データ修正自体は `wrangler d1 execute --command '...'`（または管理画面経由）で実行し、
     修正内容は必ず監査ログ（`activity_log`）に記録する
4) 月次 Payout 集計バッチ（Cron Triggers）が誤って実行された場合は、コードのロールバックとは別に
   `wrangler.jsonc` の `triggers.crons` を一時的に空にして再デプロイし、次回実行を止める
   （バッチ結果自体はコードのロールバックでは戻らない — DEV-08 §5「即時停止」参照）。
   対象 `payouts` レコードは `on_hold` へ手動遷移させ（DEV-09 §2-9）、Stripe 側の Transfer 実績と
   突合の上で修正後に再実行する
5) セッション（`admin_sessions` / `walker_sessions` / `organization_sessions`）は D1 に永続化されており
   コードのロールバックだけでは影響を受けないが、ロールバック対象の変更が認証・セッション処理自体に
   関わる場合は、影響を受けた系統のセッション行のみを個別に削除し、当該系統の再ログインを促す
   （3 系統は完全分離のため他系統には波及しない — GOV-01 D-004・D-007）
6) ロールバック実施を §2 のインシデントとして記録（P0/P1 相当なら GOV-01 にふりかえり）
```

### 3-4. 緊急リリース（Hotfix）

```
1) main から hotfix ブランチを作成（hotfix/短い説明）
2) 修正 + 関連テスト・静的解析・フォーマッタを通す
3) PR 作成 → 承認は Tech Lead（兼務可）。P0 対応時は事後レビュー可
4) マージ → 自動デプロイ（§3-1 の 3）→ §3-1 の 4〜7 を実施
5) 修正を開発ブランチにも反映
```

### 3-5. 計画停止（メンテナンスモード）

停止を伴う作業（大規模マイグレーション等）は、OPS-01 §3-4 の通知条件（7 日前通知・月 1 回まで）を満たした上で、KV フラグ + 各アプリの `src/middleware.ts` 判定によるメンテナンスモードで実施する。月次 Payout 集計バッチの実行時刻（Cron Triggers）と計画停止の時間帯が重ならないよう事前に確認する。作業完了後に §3-1 の 4〜5 を実施する。

## 4. バックアップ・データ保持

### 4-1. バックアップ方針

DB は Cloudflare D1（Cloudflare マネージドの SQLite 互換データベース）を使用する。D1 には **Time Travel（ポイントインタイムリカバリ）が常時有効**で、分単位の任意時点へ追加コストなしで復元できる（保持: Workers Paid 30 日 / Free 7 日 — 2026-08 確認）。これを第一の復旧手段とし、保持期間を超える長期保管・オフサイト保管が必要な場合のみ `wrangler d1 export` による日次エクスポートを併用する。

| 対象 | 方式 | 頻度 / 保持 |
| --- | --- | --- |
| DB（Cloudflare D1） | Time Travel（常時有効・PITR。復元は `wrangler d1 time-travel restore`）+ 長期保管が必要な場合のみ `wrangler d1 export` 併用 | Time Travel: 30 日（Paid）/ 7 日（Free）。export 併用時: 日次 / 30 日超 |
| オブジェクトストレージ（R2。保護犬・保護団体の写真、団体審査の申請書類・本人確認書類、お散歩記録の写真） | 重要書類（団体審査の申請書類・本人確認書類）は別バケットへの複製、写真は再アップロード可能な低優先資産として複製対象外 `[Assumed: 事業責任者確認]` | 日次 / 30 日 |
| 監査ログ（`activity_log`） | 削除不可・永続保持（PRD-02 §8）。D1 のバックアップに含めた上で長期保管先を確保 | 永続 |

### 4-2. RTO / RPO 目標（軽量版）

| 区分 | RTO（復旧目標） | RPO（許容データ損失） |
| --- | --- | --- |
| DB 全損 | 1 営業日 | 24 時間（バックアップ間隔） |
| オブジェクトストレージ部分損失 | 1 営業日 | 24 時間 |
| 監査ログ | — | 0（永続化必須） |

### 4-3. データ保管期限の自動削除バッチ・月次 Payout 集計バッチ

保持期間の一覧は **DEV-07 §10（PRD-02 §8 を論理的な正本とし物理設計へ反映したもの）を正本** とし、本節では再掲しない。バッチの起動方法は Cloudflare Cron Triggers（`Decided` — GOV-01 D-010）で、`apps/admin` の `wrangler.jsonc` の `triggers.crons` に日次・月次の cron 式を定義し、対応する単一の Scheduled Worker（`apps/admin/src/scheduled.ts` 相当）内で `event.cron` の値に応じて処理を分岐する。

```ts
// 毎日 03:00 JST 実行（データ保管期限の自動削除。保持期間・対象テーブルは DEV-07 §10 が正本）
expireInvitations(); // 発行から 30 日経過の invitations を物理削除（DEV-09 §2-3）
purgeExpiredSessions(); // 期限切れの admin_sessions / walker_sessions / organization_sessions を物理削除（3 系統は独立運用）
purgeDelistedDogsAndWalkSlots(); // 掲載終了（unpublished/closed）後 1 年経過の dogs / walk_slots / walk_slot_dogs / walk_records を物理削除
purgeSettledPaymentsAndPayouts(); // 決済日から 7 年経過の reservations / payments / payouts を物理削除対象として抽出（会計要件 — 実運用は事業責任者・税理士確認後に有効化）
purgeIncidents(); // 保持期間経過の incidents を物理削除（保持期間は [Open] — GOV-02 TBD-22、暫定 5 年）
purgeAdoptionInquiries(); // 保持期間経過の adoption_inquiries を物理削除（保持期間は [Open] — GOV-02 TBD-33、暫定 3 年）
purgeExpiredInquiries(); // 受信 1 年経過の inquiries を物理削除（個人情報を含むため）
cleanupOrphanedMedia(); // どの Dog/Organization/WalkRecord からも参照されない media を削除（D1 DELETE + R2 オブジェクト削除、参照切れから 90 日）
cleanupNotifications(); // 90 日経過した notifications を削除

// 毎月 1 日 04:00 JST 実行（月次 Payout 集計バッチ。`Decided` — GOV-01 D-010、DEV-08 §1）
aggregateMonthlyPayouts(); // 前月分の確定済み payments を organization_id 単位で集計し payouts を confirmed へ（DEV-09 §2-9）、
                           // 確定分について Stripe Connect Transfer を実行し paid へ遷移（DEV-07 §5-13）
```

日次バッチと月次バッチは同一 Scheduled Worker 内で `triggers.crons` の複数エントリ（日次用・月次用）を持たせ、`event.cron` の値で分岐する。`apps/public` にはデータ保管期限バッチ・Payout 集計バッチのいずれも配置しない（D1 マイグレーションと同様、集計・削除の書き込み系バッチは `apps/admin` に統一 — CLAUDE.md「D1/R2/KV バインディングルール」）。

- 期限到達前にユーザーへ段階通知する（保護団体の掲載終了 1 年保管期限に対する事前通知。90 日前メール → 30 日前再通知 → 7 日前最終通知 → 削除実行後に完了通知）
- 自動削除は必ず監査ログに記録する（システム起点のため causer は NULL のまま、event: `data.purged`、発生源は properties で示す — DEV-05 §9-1）
- 事故報告（`incidents`）・里親相談（`adoption_inquiries`）の保持期間は `[Open]`（GOV-02 TBD-22, TBD-33）。確定後に削除バッチへ反映する
- 月次 Payout 集計バッチの失敗・誤集計への対応（即時停止手順）は §3-3 のロールバック実作業を参照
- 退会時のデータ保持・エクスポート条件は OPS-01 §4-2 と整合させる
- バッチの直近成功時刻は `GET /api/v1/health/batch`（`apps/admin`、DEV-08 §9）で監視する

## 5. リリース後に育てる項目

以下は本書ではあえて定義しない。**運用開始後に必要になった時点で GOV-02 に起票して整備する**。

| 項目 | 起票の目安 |
| --- | --- |
| 運用 KPI の目標値・計測（応答時間 p90、解決率、CSAT 等） | チケット量が体感で追えなくなったら |

## 6. 記入時チェックポイント

- §1 の受付時間・チャネルが実際の体制人数（兼務前提）で守れるか
- OPS-01 §3-3 の一次応答 SLA と §1 の受付時間が矛盾していないか
- Severity 定義（§2-1）がシステム障害と動物・人的安全事故の両方をカバーし、現実的か。`incidents.severity`（DEV-07 §5-15）の値と一致しているか
- ロールバック手順（§3-3）がリリース前に一度実際に試されているか。月次 Payout 集計バッチの即時停止手順が実行可能か
- Cloudflare のバックアップ仕様（§4-1、D1 Time Travel の保持日数）を確認し「要確認」が残っていないか
- §4-3 の削除バッチ・Payout 集計バッチの対象テーブルが DEV-07 §10・PRD-02 §8 と整合しているか
- 技術固有名が DEV-01 参照になっているか（本書に選定を書いていないか）

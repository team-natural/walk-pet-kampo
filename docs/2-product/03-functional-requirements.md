# 03-functional-requirements.md — 機能要件定義

## このセクションの目的

提供すべき機能、MVP スコープ、受け入れ条件、非機能要件を定義する。本サービスは二者間マーケットプレイス（お散歩参加者 Walker × 保護団体 Organization、運営 Platform の 3 者構造）であり、テンプレート標準の機能グループ構成（コンテンツ主体サイト向けの FG-01〜07）ではなく、マーケットプレイス固有の機能グループ（FG-01〜15）を独自に定義する（`Decided` — GOV-01 D-006）。チャット・AI 機能は旧仕様の不採用判断をそのまま継承し（`Decided` — GOV-01 D-005）、本書の機能一覧から除外する。

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 草案 + PdM 主導で確定）
- 人間確認必須: MVP 判断、優先度、非機能数値、受入条件の妥当性

## 2. 機能一覧

### FG-01 認証・本人確認

| 機能 ID | 機能名 | 優先度 | MVP | 関連エンティティ |
| --- | --- | :---: | :---: | --- |
| F-01-01 | メールアドレス確認 | High | ○ | Walker |
| F-01-02 | 電話番号確認（SMS。**初回予約時**に実施 — GOV-01 D-036）| High | ○ | WalkerProfile |
| F-01-03 | ログイン / ログアウト | High | ○ | Walker |
| F-01-04 | パスワードリセット | High | ○ | Walker |
| F-01-05 | 年齢確認（生年月日入力・保護者同伴要件の判定）| High | ○ | WalkerProfile |
| F-01-06 | 利用規約・誓約事項への同意 | High | ○ | Walker, WalkerProfile |
| F-01-07 | ソーシャルログイン（Google 等）| Medium | △ | Walker |

> **F-01-02 は「登録時の全員」ではなく「初回予約時の予約者」に対して行う**（`Decided` — GOV-01 D-036）。登録しただけで予約しない利用者にも SMS を送る設計では、送信費用が 1 予約あたりの運営取り分（BIZ-03 §2-1: 参加費 ¥500 − 団体還元 ¥400）を上回りうるため。安全上の目的（当日の到達性・制限措置の実効性）が実際に要る地点は予約なので、確認をそこへ寄せても要件は落ちない。`pending_verification → active` の条件はメール確認 + 規約同意に変更（DEV-09 §2-4-3）、予約作成の前提に電話確認を追加（同 §2-7-3）。
>
> SMS の**送信手段そのものは未確定**（`Open` — GOV-02 TBD-61）。必要になるのは DEV-11 P11（予約確保）であり、保険・責任分担（TBD-17/18/20）の結論次第で本人確認の水準ごと見直す可能性がある。

認証実装は 3 系統に完全分離する（`Decided` — GOV-01 D-011・D-007、詳細は DEV-01 §1「アカウント系統」）：Walker（お散歩参加者）は `apps/public` の Member（`/mypage/*`）、保護団体スタッフは `apps/public` の OrganizationMember（`/organization/*`、`org_admin` / `org_staff`）、プラットフォーム運営者は `apps/admin` の AdminUser（単一ロール `admin`）。いずれも別テーブル・別セッションクッキーで、ライブラリは使わず自前実装する（DEV-01 §2「API 提供（認証）」）。本節の F-01-01〜07 は `apps/public` 側（Walker・OrganizationMember）の認証機能を指す。AdminUser（`apps/admin`）側の管理画面ログインはテンプレート標準機能として別途実装し、本書では独立した機能 ID を付与しない。

## 3. ユーザーストーリー（主要のみ）

### US-01 お散歩参加者の初回予約

- **As a** お散歩参加者
- **I want** エリアと日付でお散歩募集を検索し、その場でオンライン決済して予約したい
- **So that** 気軽に保護犬と触れ合う体験ができる
- 関連 KPI: KPI-02（予約充足率）, KPI-05（参加者リピート率）
- 関連機能 ID: F-07-01, F-07-03, F-07-05, F-07-06, F-08-01

### US-02 保護団体の登録・初回お散歩枠公開

- **As a** 保護団体の代表者
- **I want** 登録申請から審査完了までの流れが明確で、承認後すぐにお散歩枠を公開したい
- **So that** 早期に参加者を集め活動資金を得られる
- 関連 KPI: KPI-03（団体オンボーディング完了率）
- 関連機能 ID: F-03-01, F-03-04, F-03-06, F-06-01, F-06-02

### US-03 団体スタッフの日常運用

- **As a** 保護団体スタッフ
- **I want** 予約者情報と当日の担当犬をまとめて確認し、実施結果をその場で記録したい
- **So that** 予約管理の手作業をなくし、参加者への信頼を積み上げられる
- 関連機能 ID: F-06-03, F-10-01

### US-04 参加費決済とキャンセル

- **As a** お散歩参加者
- **I want** 予約後に予定が合わなくなった場合、キャンセル条件に沿って返金してほしい
- **So that** 安心して予約できる
- 関連機能 ID: F-08-03, F-08-06

### US-05 団体還元の可視化

- **As a** 保護団体の代表者
- **I want** 月次でいくら還元されるか・いつ振り込まれるかを確認したい
- **So that** 活動資金の見通しを立てられる
- 関連 KPI: KPI-08（テイクレート収益成長率）
- 関連機能 ID: F-09-02, F-09-04

### US-06 里親相談への橋渡し

- **As a** お散歩参加者
- **I want** 気に入った保護犬について里親相談を送りたい
- **So that** 将来の家族としての可能性を検討できる
- 関連 KPI: KPI-07（里親相談転換率）

## 5. 受け入れ条件フォーマット

Given / When / Then の 3 要素で記述する。

```
Given <前提条件>
When <ユーザー操作>
Then <期待結果>
And <追加の期待結果>
```

例：

```
Given お散歩参加者がメール・電話番号確認済みでログインしている
When エリア「東京都」・日付「今週末」でお散歩募集を検索し、1 件を選んで参加費を決済する
Then 予約が「予約確定」ステータスになる
And 参加者・保護団体の双方に予約完了通知が届く
And 該当お散歩枠の残り予約可能人数が 1 減る
```

### 6-2. セキュリティ

詳細は DEV-02 参照。

- 認証: D1 セッション + httpOnly 署名クッキーによる自前実装。Walker（`apps/public` の Member、`/mypage/*`）・保護団体スタッフ（`apps/public` の OrganizationMember、`/organization/*`）・プラットフォーム運営者（`apps/admin` の AdminUser）は別テーブル・別セッションクッキーの 3 系統に完全分離する（`Decided` — GOV-01 D-007、DEV-01 §1・§2、DEV-02 §1-1）
- ロール: `apps/admin` の AdminUser は単一ロール `admin`（role 列を持たず全操作を実行可能）+ `apps/public` の OrganizationMember（`organization_id` に紐づく `org_admin` / `org_staff`）の 2 系統 3 ロール（専用ライブラリは使わず自前実装、`Decided` — GOV-01 D-011、DEV-01 §1、構造の正本は PRD-01 §1-2 / DEV-02 §2）。Walker はロールを持たず、WalkerProfile（Member）の状態（status）で機能解禁を判定するデータ駆動方式（旧仕様の判断を継承）
- データ分離: Organization 側は `organization_id`、Walker 側は自身の Member ID でスコープ強制（物理カラム名は DEV-07 で確定）
- 監査ログ: 重要操作（審査・還元確定・キャンセル等）を監査ログへ記録（記録先は DEV-01 §2 の自前 D1 テーブル `activity_log`、必須記録操作は DEV-05 §9-1）
